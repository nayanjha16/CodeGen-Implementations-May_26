Slide 2 · Problem & System

Problem, answer, and architecture

One frozen base · three LoRA adapters · OpenAI-compatible gateway — trained for structured DB tasks.

Why this is hard

  • Full fine-tunes are costly on research / student hardware
  • Zero-shot CodeGen-350M is weak on structured DB tasks
  • Aligned NL ↔ SQL ↔ Mongo ↔ docs with execution proof is rare
  • IDEs need a deployable OpenAI-compatible endpoint

Our answer

  • One frozen base + 3 LoRA adapters (~40 MB each at v4)
  • Train & eval on TEND (Spider + BIRD, exec-validated)
  • FastAPI intent → set_adapter on Cloud Run / HF
  • Desktop tool: RAG schema → generate → validate → execute

Slide 3 · Dataset motivation

Why we built TEND

Spider & BIRD stop at NL→SQL. We needed one execution-validated row for all three LoRA adapters — so we built and published TEND.

Gaps we hit

  • Benchmarks stop at NL → SQL — no aligned Mongo or docs
  • Three adapters need the same gold row across all tasks
  • LLM-only synthetic Mongo is unreliable without execution filter

How we fixed it

  • Deterministic first — rules → Python tool → Ollama fallback
  • Execution is ground truth — PostgreSQL vs MongoDB must match
  • One row, three tasks — question, SQL, Mongo, and docs together

Slide 6 · The tool we built

Desktop AI SQL Assistant

Tried Cursor → scoped a VS Code extension → shipped a desktop client that owns schema RAG, safety, and execute.

3 · Shipped
Desktop AI SQL Assistant

RAG schema → generate → validate SELECT → execute on PostgreSQL.

Why Cursor alone wasn’t enough

  • Custom model reaches our gateway, but prompt construction is opaque
  • No way to inject retrieved DDL before generation
  • Without schema grounding, Text2SQL guesses table/column names

What the tool adds

  • Ask in English — get executable SQL, not a blank editor
  • Schema RAG — retrieve top-K tables (+ FKs), inject only that DDL
  • Closed loop — generate → SELECT-only validate → run → results
  • Safety — blocks non-SELECT; log shows tables chosen

Slide 7 · Roadmap

Improvements & future scope

What we would harden next — from today’s desktop + Cloud Run path to an IDE-native, execution-gated product.

Near-term

  • VS Code extension — schema index + Chat UI on the same /v1
  • Per-task decoding — beam for Text2SQL/docs; greedy for SQL2NoSQL
  • Full-split metrics — publish on full TEND test (~1.6k), not only gold-50
  • Tool tabs — finish SQL→NoSQL and Documentation flows

Mid-term

  • Execute-checked agent — NL→SQL→Mongo→docs with a DB check between steps
  • Richer schema linking — column-level retrieval; multi-DB workspaces
  • Stricter gold retrains — LoRA on highest-yield execution subsets
  • CI eval gate — gold-50 exec smoke before Cloud Run deploy

Longer-term

  • Larger base LM — 1–2B code model + same LoRA recipe
  • Preference / DPO — learn from fluent-but-wrong SQL
  • On-device adapters — privacy-first MPS / DirectML path
  • Multi-user serving — API keys and quotas on Cloud Run
Today: Desktop tool + Cursor base URL + HF adapters → Next: VS Code extension → Then: agent with execution gates

Known ceilings

  • 350M base limits hard multi-table / nested queries
  • Text2SQL still trails SQL2NoSQL (60% vs 88% exec)
  • Doc quality still partly LLM-judged

What stays fixed

  • Execution as ground truth (TEND-style match)
  • One frozen base + swappable LoRA adapters
  • OpenAI-compatible gateway — clients own schema & DB
